# Feature Specification: Audit Storage & Query

**Feature Branch**: `012-kit-012-audit`  
**Created**: 2026-06-10  
**Status**: Draft  
**Input**: User description: "KIT-012 Audit Storage & Query - Implement a complete Audit Storage & Query subsystem for Kit Logger. This subsystem is responsible for persisting, indexing, querying, retaining, and retrieving audit events produced by KIT-011 Audit Capture. Audit Storage & Query must remain independent from Operational Logging and Security Logging and focus exclusively on long-term audit event management."

## Relationship with KIT-011

**Input**: AuditEvent produced by [KIT-011 Audit Capture](https://github.com/pablogore/kit-config/blob/main/specs/011-kit-011-audit/spec.md)

- KIT-011 provides: `AuditEvent`, `AuditLogger`, `AuditPipeline`, `AuditExporter`
- KIT-012 consumes: `AuditEvent` and its associated `ComplianceMetadata`

**Output**: 
- Stored Persistent Audit Records
- Query Results
- Compliance Reports
- Export Files

## Architecture

```
AuditEvent (from KIT-011)
        ↓
   AuditStore (persistence layer)
        ↓
   IndexManager (indexing layer)
        ↓
   AuditQueryStore (query/filter layer)
        ↓
   QueryEngine (search engine)
        ↓
   ReportEngine (compliance reports)
        ↓
   ExportService (export formats)
```

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Store and Retrieve Audit Events (Priority: P1)

As a system administrator, I need to persistently store all audit events generated by KIT-011 Audit Capture so that they can be retrieved later for compliance and investigation purposes.

**Why this priority**: This is the foundational capability - without persistent storage and retrieval, the entire Audit Storage & Query subsystem has no purpose. All other features depend on events being reliably stored.

**Independent Test**: Can be fully tested by storing a batch of audit events and retrieving them by event ID, verifying complete event data preservation including timestamps, actor information, and action details.

**Acceptance Scenarios**:

1. **Given** an AuditEvent produced by KIT-011 Audit Capture, **When** the event is submitted to Audit Storage, **Then** the event is persisted to durable storage and a unique event ID is returned
2. **Given** a stored audit event with a known event ID, **When** a retrieval request is made, **Then** the complete original event data is returned including all metadata
3. **Given** multiple audit events from different sources, **When** they are stored, **Then** each event maintains its original timestamp ordering and can be retrieved in chronological sequence

---

### User Story 2 - Search and Filter Audit Events (Priority: P2)

As a compliance officer, I need to search and filter audit events by various criteria (date range, actor, action type, resource) so that I can find relevant events quickly without scanning all events.

**Why this priority**: Compliance investigations and audits require finding specific events among potentially millions. Without effective search, the system is not usable for its intended purpose.

**Independent Test**: Can be tested by storing 1000+ events with varied attributes, then searching with different filter criteria and verifying only matching events are returned.

**Acceptance Scenarios**:

1. **Given** a repository containing 10,000 audit events spanning 6 months, **When** a search is performed with a date range filter, **Then** only events within that date range are returned
2. **Given** audit events with different actor identifiers, **When** a search is performed filtering by actor, **Then** only events performed by that actor are returned
3. **Given** audit events with different action types (create, read, update, delete), **When** a search filters by action type, **Then** only matching events are returned

---

### User Story 3 - Configure and Enforce Retention Policies (Priority: P2)

As a compliance manager, I need to define how long audit events are retained so that the system automatically manages storage size while meeting regulatory requirements.

**Why this priority**: Different industries and regulations have varying retention requirements (SOX requires 7 years, PCI-DSS requires 1 year, etc.). Manual deletion is error-prone and non-compliant.

**Independent Test**: Can be verified by setting a retention policy, waiting for or simulating the passage of time, and confirming events beyond the retention period are automatically purged.

**Acceptance Scenarios**:

1. **Given** a retention policy specifying 90 days, **When** an audit event is 91 days old, **Then** that event is automatically removed from storage
2. **Given** multiple retention policies for different event categories, **When** events are evaluated, **Then** each event is handled according to its category's policy
3. **Given** a compliance requirement mandating minimum 1-year retention, **When** a policy is set to 6 months, **Then** the system warns about the non-compliant configuration

---

### User Story 4 - Export Audit Data for External Review (Priority: P3)

As an external auditor, I need to export audit events in a standard format so that I can analyze them using my own tools and perform independent compliance verification.

**Why this priority**: External auditors and regulatory bodies often require data exports in specific formats (CSV, JSON, SIEM formats) for independent analysis.

**Independent Test**: Can be tested by exporting events within a date range and verifying the exported file contains all matching events in the correct format with complete data.

**Acceptance Scenarios**:

1. **Given** a date range selection, **When** an export is triggered, **Then** a file is generated containing all events in that range in the requested format
2. **Given** an export request for JSON format, **When** the file is generated, **Then** the exported JSON is valid and parseable
3. **Given** an export of 100,000+ events, **When** the export is requested, **Then** the system can generate the export without timing out and the file contains all requested events

---

### User Story 5 - Generate Compliance Reports (Priority: P3)

As a compliance officer, I need automated compliance reports showing who accessed what resources and when, so that I can demonstrate regulatory compliance without manual effort.

**Why this priority**: Many regulations (SOX, HIPAA, PCI-DSS) require periodic audit reports. Manual generation is time-consuming and error-prone.

**Independent Test**: Can be tested by generating a report for a defined period and verifying it contains accurate summaries of all activities, access patterns, and meets the expected format.

**Acceptance Scenarios**:

1. **Given** a date range, **When** a compliance summary report is generated, **Then** the report includes totals for each action type, unique actors, and unique resources accessed
2. **Given** a report request for user access activity, **When** the report is generated, **Then** it shows each user's total actions and the resources they accessed

---

### Edge Cases

- What happens when storage reaches capacity limits? (System must either reject new events or implement graceful degradation with warnings)
- How does the system handle duplicate event submissions? (Must maintain idempotency - same event ID returns SUCCESS NO-OP, not error)
- What happens when querying with contradictory filters (e.g., date range with no overlap)? (System returns empty results with clear message)
- How does the system handle events from KIT-011 that are malformed or missing required fields? (Must log rejection reason and provide recovery mechanism)
- What happens during storage backend failures? (System must provide clear error messages and not lose in-flight events)
- How is the system protected against unauthorized access to audit data? (Only authorized personnel can query/export audit data)
- What happens when two identical queries return different orderings? (System MUST use deterministic ordering: ORDER BY timestamp ASC, event_id ASC)
- What happens to events when retention period expires with strategy=ArchiveThenPurge? (System signals archive intent; archive storage is implemented by storage providers per FR-009d)
- What happens to events when RetentionPolicy has legal_hold=true? (Events MUST NOT be deleted regardless of age)
- Where is archive storage implemented? (Archive storage is OUTSIDE KIT-012 scope - storage backends may optionally implement it)

## Requirements _(mandatory)_

### Functional Requirements

#### Core Storage (AuditStore - Append-Only)

- **FR-001**: The system MUST provide an `AuditStore` trait with the following contract:
  - `append(&self, event: AuditEvent) -> Result<()>` - Persist an audit event (append-only, no updates)
  - `get(&self, event_id: EventId) -> Result<Option<AuditEvent>>` - Retrieve by ID
  - `exists(&self, event_id: EventId) -> Result<bool>` - Check existence
  - `count(&self) -> Result<u64>` - Total event count

**AuditStore Constraints:**
- **NO update operations** - Events are immutable once stored
- **NO delete operations** - Deletion only through RetentionEngine
- **Only append operation** - New events can be added, existing events cannot be modified

- **FR-002**: The system MUST persist audit events to durable storage with guaranteed write confirmation
- **FR-003**: The system MUST preserve and index the `event_id` generated by KIT-011 (UUID v7), not generate new identifiers
- **FR-004**: The system MUST support retrieval of audit events by their unique identifier

#### Query Interface (AuditQueryStore)

- **FR-005**: The system MUST provide an `AuditQueryStore` trait returning paginated results:
  - `find_by_actor(actor: &str, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Filter by actor
  - `find_by_action(action: &ActionType, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Filter by action type
  - `find_by_resource(resource: &str, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Filter by resource
  - `find_by_time_range(start: DateTime, end: DateTime, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Date range filter
  - `find_by_correlation_id(correlation_id: &str, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Correlation ID lookup
  - `search(query: &str, filters: QueryFilters, pagination: PaginationRequest) -> Result<PagedResult<AuditEvent>>` - Full-text search with filters

- **FR-005a**: The system MUST define a `PagedResult<T>` or `AuditQueryResult` structure containing:
  - `items: Vec<T>` - The page of results
  - `total: u64` - Total count matching query
  - `next_cursor: Option<String>` - Cursor for next page (for cursor pagination)
  - `has_more: bool` - Whether more pages exist

#### Pagination

- **FR-006**: The system MUST support two pagination strategies:
  - `OffsetPagination { offset: u64, limit: u64 }` -Traditional offset-based pagination
  - `CursorPagination { cursor: Option<String>, limit: u64 }` - Cursor-based pagination for large datasets

#### Idempotency

- **FR-007**: The system MUST handle duplicate event submissions idempotently:
  - If an event with the same `event_id` already exists, the operation MUST return `Success (NO-OP)` without error
  - The original event data MUST NOT be modified

#### Deterministic Ordering

- **FR-008**: All query results MUST use deterministic ordering: `ORDER BY timestamp ASC, event_id ASC`
- **FR-009**: Identical queries MUST return results in the same order across different executions

#### Retention Engine

- **FR-009a**: The system MUST provide a `RetentionEngine` (or `RetentionManager`) trait with the following contract:
  - `evaluate(&self, events: &[AuditEvent]) -> Result<Vec<AuditEvent>>` - Identify events eligible for purging
  - `execute(&self, events: &[AuditEvent]) -> Result<u64>` - Perform purging and return count deleted
  - `dry_run(&self) -> Result<Vec<AuditEvent>>` - Preview what would be purged without deleting

- **FR-009b**: Only the RetentionEngine MAY delete events from AuditStore
- **FR-009c**: No direct delete operation exists on AuditStore - all deletion passes through RetentionEngine
- **FR-009d**: **Archive storage behavior is OUTSIDE the scope of KIT-012**. Archive storage MAY be implemented by storage providers (PostgreSQLAuditStore, DynamoDBAuditStore, etc.) as an optional feature. KIT-012 defines the contract only - `RetentionStrategy::ArchiveThenPurge` signals when archive should occur, not how.

#### Retention Policies

- **FR-010**: The system MUST support `RetentionPolicy` with the following structure:
  ```rust
  struct RetentionPolicy {
      classification: EventClassification,    // public, internal, confidential, restricted
      duration: Duration,                       // retention period
      legal_hold: bool,                         // legal hold flag - overrides retention
      strategy: RetentionStrategy,             // purge or archive_then_purge
  }
  
  enum RetentionStrategy {
      Purge,            // Permanently delete events after retention period
      ArchiveThenPurge, // Move to cold storage before deletion
  }
  ```
  - Default strategy is `ArchiveThenPurge` for compliance-sensitive environments
- **FR-011**: The system MUST automatically remove events that exceed their retention period
- **FR-012**: The system MUST warn administrators when configured retention periods fall below regulatory minimums
- **FR-013**: Events marked with `legal_hold: true` MUST NOT be automatically purged regardless of age

#### ComplianceMetadata Integration

- **FR-014**: The system MUST integrate with `ComplianceMetadata` from KIT-011:
  - Use `classification` from `ComplianceMetadata` to determine retention policy
  - Use `jurisdiction` from `ComplianceMetadata` for data residency requirements
  - Use `data_category` from `ComplianceMetadata` for filtering and reporting

#### Search & Indexing

- **FR-015**: The system MUST provide a `SearchProvider` trait for full-text search:
  ```rust
  trait SearchProvider {
      fn index(&self, event: &AuditEvent) -> Result<()>;
      fn search(&self, query: &str, filters: QueryFilters) -> Result<Vec<SearchResult>>;
  }
  ```

- **FR-015a**: The system MUST define a `SearchResult` entity containing:
  - `event: AuditEvent` - The matching audit event
  - `score: f64` - Relevance score
  - `highlights: Vec<Highlight>` - Matched text snippets

- **FR-015b**: The system MUST define a `QueryFilters` entity containing:
  - `actor_filter: Option<String>` - Filter by actor
  - `action_filter: Option<ActionType>` - Filter by action type
  - `resource_filter: Option<String>` - Filter by resource
  - `time_range: Option<DateRange>` - Filter by time range
  - `classification: Option<EventClassification>` - Filter by compliance classification
- **FR-016**: The system MUST support filtering by actor (the user or system performing the action)
- **FR-017**: The system MUST support filtering by action type (create, read, update, delete, or custom types)
- **FR-018**: The system MUST support filtering by resource (the object being acted upon)
- **FR-019**: The system MUST support date range queries to find events within a specific time window

#### Export Service

- **FR-020**: The system MUST provide an `AuditExportService` with the following methods:
  - `export_json(range: DateRange) -> Result<ExportFile>` - JSON format export
  - `export_csv(range: DateRange) -> Result<ExportFile>` - CSV format export
  - `export_jsonl(range: DateRange) -> Result<ExportFile>` - JSONL format export
- **FR-021**: The system MUST support date-range-limited exports to minimize data transfer
- **FR-022**: Export operations for up to 100,000 events MUST complete within 5 minutes
- **FR-022a**: ExportService MUST consume QueryEngine results to ensure consistent filtering logic - duplicate query paths are NOT permitted

#### Report Engine

- **FR-023**: The system MUST provide a `ReportEngine` trait for generating compliance reports:
  ```rust
  trait ReportEngine {
      fn generate(&self, request: ReportRequest) -> Result<ComplianceReport>;
      fn list_available(&self) -> Result<Vec<ReportTemplate>>;
  }
  ```

- **FR-023a**: The system MUST define `ReportRequest` containing:
  - `report_type: ReportType` - Type of report to generate
  - `date_range: DateRange` - Time period covered
  - `filters: QueryFilters` - Additional filters
  - `format: ReportFormat` - Output format (JSON, CSV, PDF)

- **FR-023b**: The system MUST define `ComplianceReport` containing:
  - `metadata: ReportMetadata` - Report generation info
  - `summary: ReportSummary` - Aggregate statistics
  - `details: Vec<ReportRow>` - Individual report entries

#### Storage Independence

- **FR-024**: The system MUST maintain independence from Operational Logging (separate storage, separate APIs)
- **FR-025**: The system MUST maintain independence from Security Logging (separate storage, separate APIs)

#### Data Integrity

- **FR-026**: The system MUST ensure audit data integrity - events cannot be modified or deleted after storage except by retention policy
- **FR-027**: The system MUST validate incoming audit events and reject malformed data with clear error messages
- **FR-028**: The system MUST provide query APIs that can handle large result sets efficiently (pagination support)

### Key Entities _(include if data is involved)_

- **AuditEvent**: The core entity representing a single audit record, containing timestamp, actor, action, resource, details, and metadata. Produced by KIT-011 Audit Capture.
- **RetentionPolicy**: Defines how long events of certain categories should be retained before automatic purging. Includes classification, duration, legal_hold, and strategy fields.
- **RetentionStrategy**: Enum defining retention behavior: `Purge` (permanent delete) or `ArchiveThenPurge` (move to cold storage before deletion)
- **AuditQuery**: A structured request specifying filter criteria (date range, actor, action type, resource, custom fields)
- **ExportJob**: Represents an ongoing or completed export operation, including status, format, date range, and result location
- **ComplianceReport**: A generated summary of audit activity for a defined period, showing aggregate statistics
- **ComplianceMetadata**: Reference to KIT-011's ComplianceMetadata - used for retention classification, jurisdiction, and data category
- **PaginationRequest**: Specifies pagination strategy (OffsetPagination or CursorPagination)
- **PagedResult<T>**: Generic paginated result container containing items, total count, next cursor, and has_more flag
- **QueryFilters**: Structured filter criteria for queries (actor, action, resource, time_range, classification)
- **SearchResult**: Full-text search result containing matched event, relevance score, and text highlights
- **RetentionEngine**: Service that evaluates and executes retention policies, being the ONLY component allowed to delete events
- **ReportEngine**: Trait defining report generation contract with `generate()` method
- **ReportRequest**: Structured request for report generation including type, date range, filters, and format

### Storage Implementation Requirements

All storage backend implementations MUST preserve the following core properties:

- **Deterministic Ordering**: All query results MUST return in consistent order (`ORDER BY timestamp ASC, event_id ASC`)
- **Append-Only Semantics**: All stores MUST only allow append operations - no in-place updates or deletes except via RetentionEngine
- **Idempotent Writes**: Duplicate `event_id` submissions MUST return success without error (NO-OP behavior)

### Storage Implementation Variants

The system SHOULD support the following storage implementations:

**MVP Phase:**
- `MemoryAuditStore`: In-memory storage for testing and development
- `FileAuditStore`: File-based persistence for single-node deployments

**Future Phases:**
- `PostgreSQLAuditStore`: RDBMS-based storage for enterprise deployments
- `SQLiteAuditStore`: Embedded database for lightweight deployments
- `DynamoDBAuditStore`: AWS DynamoDB for cloud-native deployments
- `CassandraAuditStore`: Apache Cassandra for high-volume deployments

#### Future Scalability Considerations

- **QueryPlanner** (Future Extension): At scale (10M+ events), consider adding a `QueryPlanner` component between `AuditQueryStore` and storage backends to optimize query execution plans, cache frequent queries, and route to appropriate read replicas. Not required for MVP.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Users can retrieve any stored audit event by its ID within 500 milliseconds
- **SC-002**: Date range queries returning up to 1,000 events complete within 2 seconds
- **SC-003**: The system MUST support storing at least 10 million audit events while maintaining:
  - ID lookup latency < 500ms
  - Date range query (up to 1,000 results) latency < 2s
  - Stable performance under concurrent read/write load
- **SC-004**: Retention policy enforcement runs automatically and completes within 1 hour for 1 million events
- **SC-005**: Export operations for up to 100,000 events complete within 5 minutes
- **SC-006**: Compliance reports for a one-month period generate within 30 seconds
- **SC-007**: 100% of audit events submitted to the system are confirmed as persisted before returning success to the caller
- **SC-008**: The system remains operational and continues accepting events even when backfill queries (large result sets) are running
- **SC-009**: Audit storage is demonstrably separate from operational and security logging storage paths
- **SC-010**: Identical queries return results in the same order (deterministic ordering verified by repeated queries)
- **SC-011**: Duplicate event submissions return success without error (idempotency verified)

## Assumptions

- KIT-011 Audit Capture produces `AuditEvent` with unique `event_id`
- `ComplianceMetadata` from KIT-011 is available and populated for events requiring retention classification
- The system will be deployed in an environment where storage capacity can be monitored and expanded
- Regulatory minimums for retention will be configurable by administrators
